Que hice
--------
Le agregue trazabilidad a la API: cada peticion tiene un id (X-Trace-Id) y en el
header Server-Timing se ve cuanto se demoro cada consulta a Postgres y a Mongo.
Despues medi los servicios con benchmarks de Vitest y con pruebas de carga
(1000 peticiones por endpoint) con el proyecto corriendo en Docker.


Cuanto se demoraron los servicios
---------------------------------
Endpoints (promedio por peticion):
- GET  /health                 4.68 ms
- GET  /api/postgres/health    5.83 ms
- GET  /api/postgres/users     5.59 ms
- POST /api/postgres/users     6.25 ms
- GET  /api/mongo/health       6.31 ms
- GET  /api/mongo/users        6.98 ms
- POST /api/mongo/users        6.98 ms
- GET  /api/products           5.81 ms
- POST /api/products           5.97 ms

Casi todo ese tiempo es la consulta a la base de datos (unos 2 ms), el codigo
de la API se demora menos de 0.2 ms. La API arranca en unos 280 ms.

ProductStore con 10.000 productos (antes -> despues de arreglarlo):
- list()      353 ms   -> 8.3 ms
- getBySku    64.7 us  -> 0.18 us
- create      46 us    -> 1.3 us
- update      29.9 us  -> 0.53 us
- getById     0.19 us  (ya era rapido)


Hallazgos
---------
1. list() era muy lento porque localeCompare crea un comparador nuevo cada vez
   que compara dos productos. Lo cambie por un Intl.Collator que se crea una
   sola vez y quedo 43 veces mas rapido.

2. Para buscar por sku se recorrian todos los productos. Agregue un Map de
   sku -> id y ahora buscar, crear y actualizar es mucho mas rapido.

3. Con la trazabilidad vi que en /api/postgres/users se hacia un CREATE TABLE
   en cada peticion, y eso era casi la mitad del tiempo. Ahora se hace una sola
   vez y el endpoint paso de 1249 a 1778 peticiones por segundo.

4. GET /api/products no tiene paginacion, entonces cuando hay muchos productos
   se pone lento (con 2060 productos tardaba 54 ms). No lo cambie, lo deje
   anotado.
